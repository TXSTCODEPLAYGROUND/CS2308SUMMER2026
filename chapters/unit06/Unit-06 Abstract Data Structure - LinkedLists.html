The Node — building block
Step 1
Define a simple struct in main.cpp
// main.cpp struct Node { int data; Node* next; }; int main() { Node* n1 = new Node{10, nullptr}; return 0; }
One node allocated on the heap. next = nullptr.
Step 2
Link a second node manually
// main.cpp (continued) Node* n2 = new Node{20, nullptr}; n1->next = n2; // link n1 → n2
n1->next now stores the address of n2. Non-linear: nodes live at scattered memory!
Scaling up — SinglyLinkedList

🤔 What if we need many nodes?

Manually tracking n1, n2, n3… doesn't scale.
How do we always find the first node? The last node?
How do we append without walking the entire chain every time?

Solution
Wrap nodes in a SinglyLinkedList struct
struct SinglyLinkedList { Node* head; // first node Node* tail; // last node }; // main.cpp int main() { SinglyLinkedList list{nullptr, nullptr}; // manually link last element as tail: list.head = new Node{10, nullptr}; list.tail = list.head; // single node: head == tail }

Why tail matters
Append a third node — tail does the heavy lifting
Node* n3 = new Node{30, nullptr}; list.tail->next = n3; // O(1) append! list.tail = n3; // advance tail
Without tail: walk 10→20 to find the end. With tail: jump directly to 0x7ffe_a140!

Chunked Dynamic Array
Idea
Fixed-width chunks linked together — grows without reallocating one giant block

Each chunk holds up to 100 elements. When a chunk is full, allocate a new chunk and link it — just like a linked list, but each node is an array.

Structs
const int CHUNK_SIZE = 100; struct ArrayChunk { int data[CHUNK_SIZE]; int count; // filled slots (0–100) ArrayChunk* next; }; struct DynamicArray { ArrayChunk* head; ArrayChunk* tail; int total; // elements across all chunks };

When is chunked growth applicable?

✓ Good fit

  • Append-heavy — logs, streams, event buffers
  • Avoid occasional large realloc + copy of entire array
  • Size grows unpredictably; copying 1M elements is costly
  • Mostly sequential access (iterate), not random arr[i]

✗ Poor fit

  • Frequent random index access — arr[50000]
  • Need contiguous memory (SIMD, GPU, C APIs)
  • Insert/delete in the middle often
  • Tight memory — extra next pointer per chunk
Decision rule

Use chunked linked arrays when append cost and realloc pain matter more than random access speed.

Bridge from slide 10: Same head / tail / next machinery — but each node holds 100 ints instead of one. Linked list ideas at scale.

Real-world examples — click to expand
📝
Rope / text editor buffer
Xerox Cedar, Xi editor, some IDEs
▶

Large documents stored as a tree or list of string chunks instead of one giant char array.

Why chunked: Insert/delete in the middle of a 10 MB file without shifting millions of characters. Same pointer-linking idea as slide 10.

🗄️
Database storage pages
PostgreSQL, SQLite, B-trees
▶

Data stored in fixed-size pages (often 4 KB–16 KB). New rows fill a page; when full, allocate the next page.

Why chunked: Disk I/O is page-based. Growing a table means adding pages, not reallocating one massive file block.

📋
Log & event streams
Kafka segments, WAL, append-only logs
▶

Events appended to the end. When a segment fills (e.g. 1 GB), a new immutable segment is created.

Why chunked: Append-only, never rewrite old data. Readers scan sequentially — rarely need random access to event #4,000,000.

🧱
Memory allocators (slab / chunk)
jemalloc, Linux slab allocator
▶

Fixed-size slabs hold objects of the same size. When a slab is full, allocate a new slab and link it.

Why chunked: Avoids fragmentation; O(1) alloc from current slab; new slab when exhausted — same chunk-fill pattern.

🎮
Game replay & telemetry
Frame buffers, sensor streams
▶

Long play sessions record frame-by-frame state into growing buffers. Writes are append-only for hours.

Why chunked: Steady writes without periodic copy of a multi-GB buffer. Playback iterates forward, not random access.

⚡
When std::vector wins
Contrast — the common case
▶

Game entity lists — need entities[i] every frame.
Image pixels / math buffers — SIMD needs contiguous memory.
Graph adjacency with index lookup — O(1) access is critical.

Rule: If you index into the data constantly, use std::vector.

Singly linked list

1 value per node. O(1) insert with tail. O(n) search/count/remove. Non-linear memory layout.

Chunked dynamic array

Contiguous, O(1) indexing. Default choice in C++. Realloc occasionally. Entities, pixels, math.

CS2308 takeaway: Data structures are trade-offs. Linked lists teach pointers and non-linear layout — those same ideas power real systems at scale when you combine them with fixed-size chunks.

Circular Linked List
Key idea
Last node points back to the first — tail->next = head

No nullptr at the end. The list forms a ring — you can keep walking forever.

struct CircularLinkedList { Node* head; Node* tail; }; // after building 10 → 20 → 30: tail->next = head; // close the ring
tail (30) → next points to head (10) — the circle is closed!
Walk the ring

Start at head, call curr = curr->next repeatedly — after the tail you wrap back to head. Watch the lap counter!

Unlike a linear list, a circular list has no nullptr to detect the end.
